🌿 Git & Version Control

Git is a distributed version control system built around snapshots, content addressed objects, and lightweight references. Teams rely on it not only for local history but also for branching strategy, pull request review, hooks, automation, and auditable release workflows.

Why it matters: Reliable Git usage blends internals knowledge with disciplined collaboration practices so history stays both useful and recoverable.

Overview

Objects and refs

Blobs, trees, commits, tags, refs, and HEAD define how Git stores content and points to history.

Branching models

GitFlow, GitHub Flow, and trunk based development each optimize for different release rhythms and team sizes.

Pull request workflow

PRs combine branch isolation, code review, status checks, and protected branch policies for safe collaboration.

Hooks and automation

Local hooks and GitHub Actions can enforce linting, testing, formatting, and release steps around every change.

Architecture and Components

Git stores snapshots as objects, moves lightweight refs like branches and tags across those objects, and synchronizes history with remotes through fetch, push, pull, and pull request workflows.

graph TD
  Worktree[Working Tree] --> Index[Index]
  Index --> Commit[Commit]
  Commit --> Tree[Tree Object]
  Tree --> Blob[Blob Objects]
  Commit --> Ref[Branch Refs]
  Ref --> HEAD[HEAD]
  Commit --> Remote[Remote Repository]
  Remote --> PR[Pull Request]
  PR --> Actions[GitHub Actions]
  • The working tree contains current files, the index tracks staged content, and commits persist snapshots plus parent relationships.
  • Branches are movable refs, tags mark important history points, and HEAD identifies the currently checked out ref or commit.
  • GitFlow uses long lived release branches, GitHub Flow favors short lived feature branches into main, and trunk based development minimizes branch lifetime even further.
  • Pull requests add review, discussion, and status checks before merges land on protected branches.
  • Hooks such as pre commit and pre push help catch problems locally, while GitHub Actions provides CI automation in the remote platform.

Key Concepts

Concept Purpose Operator note
Rebase Replays commits on a new base to keep history linear. Use carefully on local or unshared history and communicate before rewriting shared branches.
Cherry pick Applies a specific commit onto another branch. Useful for hotfix backports and selective promotion.
Stash Temporarily shelves working tree and index changes. Helpful for quick context switches, but avoid treating it as long term storage.
Hooks Scripts that run on local repository events such as commit or push. Keep hooks fast and documented so developers trust them.
Ignore rules .gitignore keeps generated, secret, or local environment files out of version control. Review patterns so important assets are not excluded accidentally.

These commands cover the most common daily workflows for cloning, reviewing state, and moving work between branches.

Pull requests and GitHub Actions integration

Status checks and automation make branch protection meaningful instead of ceremonial.

name: ci
on:
  pull_request:
  push:
    branches: [main]
jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - run: npm test
# PR flow
git push -u origin feature/resource-guides
# open pull request in GitHub and wait for review plus checks

Best Practices

  • Choose one branching strategy that matches release cadence and document when feature branches, hotfixes, or release branches should be used.
  • Keep commits focused and descriptive so reviewing, reverting, and cherry picking changes remains safe.
  • Rebase or merge intentionally; do not rewrite shared history without agreement from the rest of the team.
  • Use protected branches, required reviews, and GitHub Actions status checks to prevent direct unvalidated changes on important branches.
  • Maintain clear .gitignore patterns and never rely on ignore rules as the only safeguard for secrets.
  • Teach conflict resolution, reflog recovery, and hook behavior so developers can recover confidently from mistakes.

Troubleshooting

Symptom Likely cause Recommended action
Merge conflicts Two branches changed overlapping lines or file structures in incompatible ways. Review both sides carefully, resolve with intent, run tests, and commit the merge or continue the rebase deliberately.
Detached HEAD confusion A commit hash or tag was checked out directly instead of a branch. Create a new branch from the current commit if work should be preserved, then switch back to the intended branch.
Rejected pushes The remote has new commits, branch protection blocks the push, or history was rewritten locally. Fetch updates, rebase or merge as required, rerun checks, and verify whether force push is allowed before using it.
Accidentally lost changes Files were restored, reset, or rebased unexpectedly. Check git reflog, inspect stash entries, and recover commits or blobs before running additional cleanup commands.
