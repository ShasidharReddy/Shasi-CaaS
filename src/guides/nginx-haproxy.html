⚖️ NGINX & HAProxy Load Balancing

NGINX and HAProxy are proven entry point technologies for reverse proxying, load balancing, TLS termination, and edge traffic policy. They are often used together or selected based on whether the environment prioritizes flexible web serving, advanced HTTP features, or extremely efficient L4 and L7 balancing.

Why it matters: The right choice depends on traffic type, observability needs, and how much application logic is allowed at the edge.

Overview

NGINX

Combines reverse proxy, static content serving, caching, TLS termination, and application aware routing in one process.

HAProxy

Excels at high performance TCP and HTTP load balancing with strong health checks, ACLs, and connection management.

TLS and rate limits

Both platforms can enforce certificates, redirects, request limits, and backend health policies at the edge.

Monitoring

stub_status and stats pages give operators direct visibility into active sessions, queueing, and backend health.

Architecture and Components

Edge traffic commonly lands on a public load balancer, flows through NGINX or HAProxy for policy enforcement and distribution, and then reaches application pools, APIs, or TCP services.

  Clients[Clients] --> Edge[Public Endpoint]
  Edge --> NGINX[NGINX]
  Edge --> HAProxy[HAProxy]
  NGINX --> WebPool[Web Servers]
  NGINX --> API[API Cluster]
  HAProxy --> WebPool
  HAProxy --> TCPPool[TCP Services]
  NGINX --> Metrics[stub_status]
  HAProxy --> Stats[Stats Page]
  Edge --> Certbot[Certbot and Lets Encrypt]
  • NGINX is often chosen when teams want URL rewrites, caching, static assets, and reverse proxying in the same service.
  • HAProxy is ideal when balancing efficiency, advanced health checks, and traffic control for both HTTP and raw TCP streams is the priority.
  • Lets Encrypt and Certbot can automate certificate issuance and renewal for either stack, though reload workflows should be tested carefully.
  • Rate limiting, connection limits, and ACLs protect backends from abuse and help preserve fair usage during unexpected spikes.
  • Operational visibility should include backend state, request latency, TLS failures, and queue growth at the edge.

Key Concepts

Concept Purpose Operator note
Reverse proxy Terminates client connections and forwards requests to internal backends. Useful for hiding topology, applying policy, and offloading TLS.
Health checks Continuously verify backend availability before traffic is sent. Tune intervals and thresholds to avoid flapping.
ACLs HAProxy ACLs and NGINX conditionals steer traffic based on hosts, paths, headers, or rates. Keep edge logic understandable and version controlled.
SSL termination Decrypts TLS at the edge so certificates and ciphers can be managed centrally. Re encrypt to backends when compliance requires end to end TLS.
Connection control Rate and connection limits prevent overload and noisy neighbor traffic patterns. Combine with monitoring so limits are visible and tunable.

Essential Commands and Configuration

NGINX reverse proxy and rate limits

Use upstream pools, health aware timeouts, and explicit limit zones to keep web traffic predictable.

http {
  upstream app_backend {
    least_conn;
    server 10.0.10.11:8080 max_fails=3 fail_timeout=30s;
    server 10.0.10.12:8080 max_fails=3 fail_timeout=30s;
  }
  limit_req_zone $binary_remote_addr zone=req_limit:10m rate=20r/s;
  limit_conn_zone $binary_remote_addr zone=conn_limit:10m;
  server {
    listen 443 ssl http2;
    server_name app.example.com;
    ssl_certificate /etc/letsencrypt/live/app/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/app/privkey.pem;
    location / {
      proxy_pass http://app_backend;
      proxy_set_header Host $host;
      proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
      limit_req zone=req_limit burst=40 nodelay;
      limit_conn conn_limit 50;
    }
    location /nginx_status {
      stub_status;
      allow 127.0.0.1;
      deny all;
    }
  }
}

HAProxy load balancing and ACLs

HAProxy can enforce rich traffic policy while staying extremely efficient for HTTP and TCP workloads.

global
  log stdout format raw local0
defaults
  mode http
  timeout connect 5s
  timeout client  30s
  timeout server  30s
frontend https_in
  bind *:443 ssl crt /etc/haproxy/certs/app.pem
  acl is_api path_beg /api
  http-request deny if { src_conn_rate gt 100 }
  use_backend api_back if is_api
  default_backend web_back
backend web_back
  balance roundrobin
  option httpchk GET /health
  server web1 10.0.20.11:80 check
  server web2 10.0.20.12:80 check
backend api_back
  balance leastconn
  option httpchk GET /ready
  server api1 10.0.30.11:8080 check
  server api2 10.0.30.12:8080 check
listen stats
  bind *:8404
  stats enable
  stats uri /stats
  stats refresh 10s

Lets Encrypt and validation steps

Automated certificate renewal should be paired with reload checks and expiry monitoring.

sudo certbot certonly --nginx -d app.example.com
sudo certbot renew --dry-run
sudo nginx -t
sudo systemctl reload nginx
sudo haproxy -c -f /etc/haproxy/haproxy.cfg
sudo systemctl reload haproxy

Comparison snapshot

Use a concise matrix when explaining why one edge proxy is chosen over another.

Feature                 | NGINX                     | HAProxy
HTTP reverse proxy       | Excellent                 | Excellent
Static file serving      | Native strength           | Not primary focus
TCP load balancing       | Good                      | Excellent
Advanced ACLs            | Good                      | Excellent
Operational simplicity   | Familiar web syntax       | Focused LB syntax
Stats visibility         | stub_status and logs      | Rich native stats page

Best Practices

  • Keep edge configuration in version control and validate syntax before every reload or deployment.
  • Terminate TLS with modern ciphers, automate certificate renewal, and monitor expiry long before production deadlines.
  • Use health checks that reflect real readiness instead of simple TCP success for critical HTTP services.
  • Apply rate limits and connection limits cautiously, then monitor rejected traffic so thresholds can be tuned from evidence.
  • Expose stub_status or the HAProxy stats page only on trusted networks and protect them with authentication where possible.
  • Document when NGINX is used for application aware proxying and when HAProxy is used for high scale L4 or L7 balancing so platform ownership is clear.

Troubleshooting

Symptom Likely cause Recommended action
502 or 503 responses Backends are unhealthy, timeouts are too low, or headers and upstream ports are mismatched. Test backend health endpoints directly, inspect upstream logs, and confirm proxy headers expected by the application.
TLS handshake failures Certificate chains, private keys, cipher policies, or SNI hostnames are incorrect. Run openssl s_client, verify full chain files, and check recent certificate renewals or reload errors.
Uneven backend traffic Session persistence, balancing algorithms, or slow backends are skewing distribution. Review stickiness settings, compare response times, and inspect health check state transitions.
Rate limiting blocks legitimate users The configured burst or per IP thresholds do not reflect real traffic patterns. Tune limits using traffic baselines, consider trusted proxy headers, and add exemptions for internal or health check traffic.
