☸️ Kubernetes Operations & Administration

Kubernetes operations focus on keeping the control plane healthy, workloads secure, and cluster capacity aligned with demand. Administrators need a practical model for workloads, services, access control, release tooling, and incident response at the same time.

Why it matters: Operational excellence in Kubernetes comes from understanding how resources interact, not just from memorizing YAML fields.

Overview

Control plane

API server, scheduler, controller manager, and etcd coordinate desired state and persist cluster data.

Worker nodes

Kubelet, container runtime, and kube proxy run scheduled workloads and enforce networking on each node.

Workload resources

Pods, Deployments, StatefulSets, DaemonSets, Jobs, and CronJobs each fit a specific execution pattern.

Platform controls

RBAC, quotas, limits, ConfigMaps, Secrets, and Helm shape safe multi team operations.

Architecture and Components

A healthy cluster depends on the control plane reconciling desired state into running workloads while services, ingress, and policy objects shape traffic and access around those workloads.

  Users[Operators] --> APIServer[API Server]
  APIServer --> Scheduler[Scheduler]
  APIServer --> Controller[Controller Manager]
  APIServer --> Etcd[etcd]
  Scheduler --> Nodes[Worker Nodes]
  Nodes --> Pods[Pods]
  Pods --> Services[Services]
  Services --> Ingress[Ingress]
  APIServer --> RBAC[RBAC]
  APIServer --> Config[ConfigMaps and Secrets]
  APIServer --> Quotas[Quotas and Limits]
  Helm[Helm] --> APIServer
  • Deployments manage stateless rolling updates, StatefulSets preserve identity and storage order, and DaemonSets place one pod per selected node.
  • Jobs and CronJobs are ideal for finite work such as migrations, reports, or scheduled maintenance tasks.
  • Services expose pods through stable virtual IPs, while Ingress adds HTTP routing and TLS at the edge.
  • ConfigMaps and Secrets externalize configuration so images remain environment neutral and easier to promote.
  • RBAC, ResourceQuotas, and LimitRanges keep namespaces safe when multiple teams share the same cluster.

Key Concepts

Concept Purpose Operator note
RBAC Roles, ClusterRoles, and bindings grant least privilege access to users, groups, and service accounts. Review verbs and scope carefully before using wildcards.
Resource policies Quotas and limits prevent one namespace or pod from exhausting shared capacity. Set realistic requests so scheduling and autoscaling remain meaningful.
Helm Packages Kubernetes manifests into versioned, parameterized charts. Use values files per environment and track releases declaratively.
Service exposure ClusterIP, NodePort, LoadBalancer, and Ingress present workloads at different boundaries. Choose the narrowest exposure needed for the consumer.
Pod lifecycle Pending, Running, Succeeded, Failed, and restart states reveal where scheduling or execution is blocked. Describe events first, then inspect logs and dependent resources.

Workloads, services, and configuration

Operational manifests should include explicit labels, requests, health checks, and externalized configuration.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: prod
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      serviceAccountName: api
      containers:
        - name: api
          image: ghcr.io/example/api:1.4.2
          ports:
            - containerPort: 8080
          envFrom:
            - configMapRef:
                name: api-config
            - secretRef:
                name: api-secrets
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
            limits:
              cpu: 500m
              memory: 512Mi

RBAC, quotas, and limits

Guard shared clusters by granting only required verbs and setting namespace level resource boundaries.

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: app-reader
  namespace: prod
rules:
  - apiGroups: [""]
    resources: ["pods", "services", "configmaps"]
    verbs: ["get", "list", "watch"]
---
apiVersion: v1
kind: ResourceQuota
metadata:
  name: prod-quota
  namespace: prod
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 40Gi
    limits.cpu: "40"
    limits.memory: 80Gi
---
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
  namespace: prod
spec:
  limits:
    - default:
        cpu: 500m
        memory: 512Mi
      defaultRequest:
        cpu: 100m
        memory: 128Mi
      type: Container

Best Practices

  • Use namespaces, labels, and naming conventions consistently so teams can discover, filter, and automate around resources quickly.
  • Set readiness and liveness probes, resource requests, and limits on every production workload to make scheduling and failure behavior explicit.
  • Treat Secrets, RBAC, quotas, and network policy as baseline controls rather than optional hardening tasks.
  • Package repeatable workloads with Helm or another release workflow and keep all values files in version control.
  • Monitor etcd, API server latency, scheduler health, node pressure, and workload restart patterns as cluster level indicators.
  • Document standard responses for CrashLoopBackOff, ImagePullBackOff, Pending pods, and OOMKilled so on call engineers can move quickly.

Troubleshooting

Symptom Likely cause Recommended action
CrashLoopBackOff The container exits repeatedly because startup logic, configuration, or dependency availability is broken. Review describe events, previous logs, recent config changes, and probes that may be forcing early restarts.
ImagePullBackOff Image name, registry auth, image policy, or network egress is incorrect. Confirm the image tag exists, test imagePullSecrets, and inspect node level registry connectivity.
Pending pods No node matches resource requests, taints, affinities, or volume requirements. Describe the pod, inspect scheduler events, and compare requests against allocatable node capacity.
OOMKilled Memory limits are too low or the workload leaks memory under load. Check container memory usage, increase limits carefully, and profile the application before simply raising every boundary.
