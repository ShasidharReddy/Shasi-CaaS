🪵 ELK Stack

The ELK Stack centralizes logs and search workflows by moving data from Beats through Logstash into Elasticsearch and presenting it in Kibana. It is powerful for infrastructure operations, security analysis, troubleshooting, and business event exploration when pipelines and index design are disciplined.

Why it matters: Index strategy, field mappings, and lifecycle policies influence ELK performance more than dashboard polish.

Overview

Beats

Filebeat and other lightweight shippers collect logs and metrics close to the source and forward structured events.

Logstash

Provides input, filter, and output pipelines for parsing, enrichment, routing, and normalization.

Elasticsearch

Stores and indexes events across shards and replicas for search, aggregations, and analytics.

Kibana

Surfaces discover queries, visualizations, dashboards, Lens views, and alerting workflows.

Architecture and Components

A production ELK deployment balances ingest throughput, index management, and search performance so operators can move from raw events to actionable insights without overwhelming the cluster.

graph TD
  Hosts[Servers and Apps] --> Filebeat[Filebeat]
  Filebeat --> Logstash[Logstash]
  Logstash --> Elasticsearch[Elasticsearch]
  Elasticsearch --> Kibana[Kibana]
  Elasticsearch --> ILM[Index Lifecycle]
  Kibana --> Dashboards[Dashboards]
  Kibana --> Discover[Discover]
  Kibana --> Lens[Lens]
  • Filebeat is usually the first collector, reading container logs, files, or system journals and attaching metadata before forwarding events.
  • Logstash pipelines chain inputs, filters, and outputs so unstructured logs can be parsed into consistent fields.
  • Elasticsearch index templates and mappings decide how fields are stored, searched, and aggregated across shards.
  • Kibana Discover is ideal for ad hoc investigation, while dashboards and Lens are better for repeatable operational and business views.
  • Index Lifecycle Management automates rollover, warm or cold movement, and retention so storage cost stays predictable.

Key Concepts

Concept Purpose Operator note
Indices and aliases Indices hold documents while aliases provide stable names for searches and rollovers. Use date based or data stream strategies for time series logs.
Shards and replicas Primary shards distribute data and replicas improve resilience and read scaling. Too many shards waste memory; right size them for node count and query patterns.
Mappings Control data types, analyzers, and keyword versus text behavior. Explicit mappings prevent expensive surprises from dynamic field expansion.
Pipeline filters grok, dissect, mutate, date, and geoip enrich and normalize events. Keep filters simple and test them with representative log samples.
ILM Automates rollover, retention, and tiering for indices. Attach policies through templates instead of managing each index manually.

Essential Commands and Configuration

Filebeat configuration

Start with lightweight collection close to the source and add processors for metadata and multiline handling only where needed.

filebeat.inputs:
  - type: filestream
    id: app-logs
    paths:
      - /var/log/app/*.log
    parsers:
      - multiline:
          type: pattern
          pattern: "^\d{4}-\d{2}-\d{2}"
          negate: true
          match: after
processors:
  - add_host_metadata: {}
  - add_cloud_metadata: {}
output.logstash:
  hosts: ["logstash:5044"]

Logstash pipeline example

Filters should normalize timestamps and fields before Elasticsearch mappings lock in the wrong data types.

input {
  beats {
    port => 5044
  }
}
filter {
  grok {
    match => { "message" => "%{TIMESTAMP_ISO8601:timestamp} %{LOGLEVEL:level} %{GREEDYDATA:msg}" }
  }
  date {
    match => ["timestamp", "ISO8601"]
  }
  mutate {
    rename => { "host.name" => "host_name" }
  }
}
output {
  elasticsearch {
    hosts => ["http://elasticsearch:9200"]
    index => "app-logs-%{+YYYY.MM.dd}"
  }
}

Elasticsearch and ILM operations

Basic cluster checks should be part of every operator runbook before deeper query tuning starts.

curl -s http://localhost:9200/_cluster/health?pretty
curl -s http://localhost:9200/_cat/indices?v
curl -s http://localhost:9200/_cat/shards?v
curl -s http://localhost:9200/app-logs-*/_mapping?pretty
PUT _ilm/policy/logs-hot-warm-delete
{
  "policy": {
    "phases": {
      "hot": {
        "actions": {"rollover": {"max_size": "50gb", "max_age": "7d"}}
      },
      "delete": {
        "min_age": "30d",
        "actions": {"delete": {}}
      }
    }
  }
}

Kibana usage patterns

Use Discover for raw search, Lens for quick visual composition, and dashboards for shared operational views.

GET /app/discover
GET /app/dashboards
GET /app/lens
# useful search DSL
GET app-logs-*/_search
{
  "size": 0,
  "query": {
    "bool": {
      "filter": [
        {"range": {"@timestamp": {"gte": "now-15m"}}},
        {"term": {"level.keyword": "ERROR"}}
      ]
    }
  },
  "aggs": {
    "by_service": {"terms": {"field": "service.keyword"}}
  }
}

Best Practices

  • Define index templates, mappings, and ILM policies before broad ingestion starts so field types and rollover behavior stay controlled.
  • Avoid high shard counts and tiny indices; tune shard sizing to node memory, retention, and expected query concurrency.
  • Parse important fields once in Logstash or ingest pipelines and standardize names so Kibana dashboards are portable.
  • Use Filebeat processors and module defaults where possible rather than overcomplicating every Logstash pipeline.
  • Monitor ingestion lag, rejected indexing requests, JVM heap, disk watermarks, and search latency as platform level signals.
  • Reserve Kibana dashboards for high value views and retire ad hoc experiments that confuse ownership or duplicate existing searches.

Troubleshooting

Symptom Likely cause Recommended action
Yellow or red cluster health Nodes are unavailable, replicas cannot be assigned, or disks crossed watermarks. Inspect _cluster/health, _cat/allocation, node status, and adjust allocation or free disk before restarting services blindly.
Unassigned shards Replica counts exceed available nodes, index settings conflict with tiers, or disk allocation is blocked. Use the allocation explain API, reduce replica requirements temporarily, and review data tier filters.
Slow queries and dashboards Mappings are inefficient, shard counts are high, or broad wildcard searches scan too much data. Use filtered time ranges, keyword fields for exact matches, and profile representative slow queries.
Ingest pipeline backlog Logstash workers, Elasticsearch bulk settings, or downstream indexing capacity are insufficient. Increase pipeline workers carefully, inspect persistent queue depth, and verify Elasticsearch thread pools and heap usage.
