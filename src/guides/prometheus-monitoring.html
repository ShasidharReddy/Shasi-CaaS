📈 Prometheus Monitoring

Prometheus is the de facto metric collection and alerting platform for cloud-native systems. It combines pull-based scraping, dimensional time series, flexible PromQL queries, and ecosystem integrations to help operators observe infrastructure, applications, and service reliability in one workflow.

Why it matters: A healthy Prometheus deployment depends on disciplined metric design, predictable scrape targets, and recording rules that turn raw telemetry into fast dashboard and alert queries.

Overview

Prometheus Server

Scrapes targets, stores local TSDB blocks, evaluates rules, and exposes a query API for dashboards and automation.

Exporters

Translate host, network, database, and application internals into Prometheus metrics that can be scraped on a schedule.

AlertManager

Deduplicates, groups, silences, and routes alerts to email, chat, PagerDuty, or incident management systems.

Pushgateway

Handles short lived jobs that cannot be scraped directly, but should be used carefully so metrics do not become stale.

Architecture and Components

A production deployment usually places Prometheus near the workloads it scrapes, adds AlertManager for notifications, and forwards long term data through federation or remote write pipelines.

  • Prometheus servers usually separate infrastructure scraping from application scraping so retention and cardinality can be tuned independently.
  • node_exporter covers CPU, memory, filesystem, and network health, while blackbox_exporter checks endpoints, DNS, TCP, and TLS reachability.
  • mysqld_exporter and redis_exporter expose database specific counters such as replication lag, connections, slow queries, cache hits, and memory pressure.
  • AlertManager groups related pages, supports inhibition rules, and reduces alert noise when a parent service is already known to be failing.
  • Federation is useful for aggregating precomputed series from regional Prometheus servers, while remote write sends raw or near raw samples to external systems.

Key Concepts

Concept Purpose Operator note
PromQL Queries and aggregates time series with label filtering, arithmetic, rates, and vector matching. Prefer rate or increase for counters and avg_over_time for recent trends.
Recording rules Precompute expensive expressions into new metrics for dashboards and alerting. Use them for SLO windows, saturation views, and common service aggregations.
Alert rules Evaluate PromQL expressions on a schedule and create firing alerts when conditions persist. Pair with for durations to avoid paging on transient spikes.
Federation Pull selected series from another Prometheus server. Federate curated metrics instead of every raw series to keep cardinality bounded.
Remote write Push samples to long term backends such as Thanos, Cortex, or Mimir. Monitor queue pressure and retry latency so data loss is visible.

Essential Commands and Configuration

Scrape and exporter configuration

Keep scrape jobs grouped by ownership and use relabeling only when a simpler target label would not work.

global:
  scrape_interval: 15s
  evaluation_interval: 30s
scrape_configs:
  - job_name: prometheus
    static_configs:
      - targets: ['localhost:9090']
  - job_name: node
    static_configs:
      - targets:
          - web-01:9100
          - web-02:9100
  - job_name: blackbox-http
    metrics_path: /probe
    params:
      module: [http_2xx]
    static_configs:
      - targets:
          - https://api.example.com/health
          - https://shop.example.com/ready
    relabel_configs:
      - source_labels: [__address__]
        target_label: __param_target
      - source_labels: [__param_target]
        target_label: instance
      - target_label: __address__
        replacement: blackbox-exporter:9115

PromQL basics and recording rules

Recording rules reduce dashboard latency and keep alerting queries simple enough to review during incidents.

groups:
  - name: platform-recording
    interval: 30s
    rules:
      - record: job:http_requests:rate5m
        expr: sum by (job) (rate(http_requests_total[5m]))
      - record: job:http_errors:rate5m
        expr: sum by (job) (rate(http_requests_total{status=~"5.."}[5m]))
      - record: job:cpu_utilization:ratio
        expr: 1 - avg by (job) (rate(node_cpu_seconds_total{mode="idle"}[5m]))
# Example PromQL
rate(http_requests_total[5m])
sum by (instance) (rate(node_network_receive_bytes_total[5m]))
histogram_quantile(0.95, sum by (le, job) (rate(http_request_duration_seconds_bucket[5m])))
job:http_errors:rate5m / job:http_requests:rate5m

Alerting and AlertManager routing

Alert rules should describe symptoms, include labels for routing, and add annotations that point to dashboards and runbooks.

groups:
  - name: platform-alerts
    rules:
      - alert: HighErrorRate
        expr: (job:http_errors:rate5m / job:http_requests:rate5m) > 0.05
        for: 10m
        labels:
          severity: page
          team: platform
        annotations:
          summary: Elevated error rate for {{ $labels.job }}
          description: Error ratio has remained above five percent for ten minutes.
route:
  receiver: default
  group_by: [alertname, cluster, team]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
receivers:
  - name: default
    email_configs:
      - to: sre@example.com

Federation and remote write

Use federation for curated aggregate metrics and remote write when a central platform must retain long term data or support global queries.

scrape_configs:
  - job_name: federate
    honor_labels: true
    metrics_path: /federate
    params:
      match[]:
        - '{__name__=~"job:.*"}'
        - 'up{job=~"node|api"}'
    static_configs:
      - targets: ['regional-prometheus:9090']
remote_write:
  - url: https://mimir.example.com/api/v1/push
    queue_config:
      max_samples_per_send: 10000
      capacity: 20000
      max_shards: 10

Best Practices

  • Standardize labels such as service, environment, cluster, and team so dashboards and alerts can be reused across applications.
  • Control high cardinality by avoiding unbounded labels like user IDs, request paths with raw parameters, or randomly generated values.
  • Keep rule files in version control, review PromQL changes, and test expressions before promoting them into alerting.
  • Separate short retention local storage from long term remote storage so on-cluster Prometheus remains fast and predictable.
  • Monitor scrape duration, target health, TSDB compaction, WAL growth, and remote write queue pressure as first class platform signals.
  • Document runbooks next to each critical alert so responders know which dashboard, log query, or rollback path to use.

Troubleshooting

Symptom Likely cause Recommended action
High cardinality and memory growth A metric includes labels with near unlimited values such as full URLs or request identifiers. Inspect top series with tooling, remove noisy labels from instrumentation, and replace dashboard queries with recording rules.
Scrape failures or many targets down Network paths, DNS, TLS settings, or exporter processes are unhealthy. Check the Targets page, curl the exporter endpoint, validate firewall rules, and confirm scrape_timeout is lower than interval.
Storage pressure and slow queries Retention is too long for local disks or many wide range queries are scanning raw samples. Reduce retention, increase storage, add recording rules, and move historical queries to a remote backend.
Gaps in federated or remote data Source rules changed, remote write queues are backing up, or credentials were rotated. Review federation match selectors, inspect queue metrics, and verify remote endpoint authentication and ingestion quotas.
