🐳 Docker & Container Platform

Docker packages applications and dependencies into portable images that run consistently across laptops, CI pipelines, and production hosts. Modern container platforms build on Docker Engine, containerd, OCI runtimes, registries, and layered images to standardize delivery and isolation.

Why it matters: Fast builds, secure images, and clean runtime boundaries matter more than memorizing individual commands.

Overview

Docker Engine

Exposes the API, manages images, networking, volumes, and delegates low level runtime work to containerd.

containerd and runc

containerd handles lifecycle orchestration while runc launches containers according to the OCI runtime specification.

Images and registries

Images are layered immutable artifacts that can be pushed to Docker Hub or private registries for controlled distribution.

Compose

Docker Compose defines multi container applications, shared networks, environment variables, and service dependencies in YAML.

Architecture and Components

A typical Docker workflow moves from Dockerfile to image build, then to a registry, and finally to one or more runtime hosts that create containers with isolated filesystems, networking, and storage.

graph TD
  Source[Source Code] --> Dockerfile[Dockerfile]
  Dockerfile --> Build[Docker Build]
  Build --> Image[OCI Image]
  Image --> Registry[Registry]
  Registry --> Engine[Docker Engine]
  Engine --> Containerd[containerd]
  Containerd --> Runc[runc]
  Engine --> Networks[Networks]
  Engine --> Volumes[Volumes]
  Engine --> Containers[Containers]
  • Multi stage builds reduce image size by separating build time toolchains from slim runtime images.
  • .dockerignore keeps build contexts small so caches stay useful and accidental secrets are not copied into image layers.
  • Compose makes local development and small stack deployments easier by declaring services, networks, environment files, and persistent volumes together.
  • Network modes such as bridge, host, overlay, and macvlan each trade isolation, performance, and operational complexity differently.
  • Security hardening should cover rootless mode, user namespaces, seccomp profiles, AppArmor or SELinux, and minimal base images.

Key Concepts

Concept Purpose Operator note
Layer caching Reuses previous build steps when files and instructions have not changed. Place stable dependency steps before frequently changing application code.
Compose services Describe related containers, ports, networks, and volume mounts in one file. Use profiles and override files to separate local and production concerns.
Bind mounts and volumes Bind mounts expose host paths while volumes are managed by Docker. Prefer volumes for application data and bind mounts for source code during development.
Rootless mode Runs the daemon and containers without root privileges on the host. Useful for reducing host risk, though some networking features may differ.
Registries Store signed or scanned images for promotion across environments. Use private registries, immutable tags, and retention policies for production delivery.

Essential Commands and Configuration

Dockerfile best practices

Pin base images, separate dependency installation, and keep runtime layers as small and explicit as possible.

# syntax=docker/dockerfile:1
FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build
FROM nginx:1.27-alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
HEALTHCHECK CMD wget -qO- http://127.0.0.1/ || exit 1
# .dockerignore
node_modules
.git
.env
coverage

Compose for multi container apps

Compose files describe networks, dependencies, and persistent state for local stacks and small service bundles.

services:
  web:
    build: .
    ports:
      - "8080:80"
    depends_on:
      - api
    networks: [frontend]
  api:
    image: ghcr.io/example/api:1.4.2
    environment:
      DATABASE_URL: postgres://app:secret@db/app
    networks: [frontend, backend]
  db:
    image: postgres:16
    volumes:
      - dbdata:/var/lib/postgresql/data
    networks: [backend]
networks:
  frontend: {}
  backend: {}
volumes:
  dbdata: {}

Networking, volumes, and registry operations

Inspect the runtime surface area regularly so container networking and storage issues can be isolated quickly.

docker network create app-net
docker network inspect bridge
docker run --rm --network host nicolaka/netshoot ip addr
docker volume create pgdata
docker run -v pgdata:/var/lib/postgresql/data postgres:16
docker login registry.example.com
docker tag app:latest registry.example.com/platform/app:1.0.0
docker push registry.example.com/platform/app:1.0.0

Security and troubleshooting commands

Container isolation should be verified explicitly instead of assumed from defaults.

dockerd-rootless-setuptool.sh install
docker run --user 10001:10001 --read-only --cap-drop ALL nginx:1.27-alpine
docker build --progress=plain .
docker logs --tail 200 api
docker inspect api
docker system df
docker exec -it api sh

Best Practices

  • Use slim and trusted base images, pin versions, and scan images before promotion to production registries.
  • Separate build and runtime stages, and order Dockerfile instructions to maximize cache hits for dependency installation.
  • Store secrets outside images by using runtime environment injection, secret managers, or orchestrator secret stores.
  • Prefer named volumes for persistent application data and keep bind mounts limited to development or controlled debugging scenarios.
  • Harden containers with non root users, rootless engines where appropriate, seccomp, AppArmor or SELinux, and reduced Linux capabilities.
  • Monitor image pull errors, log growth, disk consumption, and orphaned layers so hosts do not degrade unexpectedly.

Troubleshooting

Symptom Likely cause Recommended action
Build failures The build context is missing files, dependency steps changed, or the base image is unavailable. Run docker build with plain progress, confirm COPY paths, and test registry reachability for the referenced base image.
Networking issues between containers Containers are on different networks, ports are not published, or host firewalls block traffic. Inspect Compose networks, use docker exec with curl or netcat, and verify service DNS names resolve inside the network.
Storage growth on hosts Dangling images, stopped containers, verbose logs, or oversized writable layers are accumulating. Review docker system df, set log rotation, prune unused artifacts carefully, and move state into managed volumes.
Application logs missing or truncated The process writes to files instead of stdout or the logging driver configuration is insufficient. Standardize structured stdout logging, inspect daemon log options, and centralize logs into Loki, ELK, or another backend.
