🛠️ Ansible Automation

Ansible automates provisioning, configuration management, deployments, and operational workflows with agentless SSH or WinRM connectivity. It scales from a single playbook run to curated role catalogs and controller based operations through AWX or Ansible Automation Platform.

Why it matters: Good Ansible content is idempotent, inventory aware, and organized so operators can understand why a change happened from the playbook structure alone.

Overview

Control node

Runs ansible and ansible-playbook, stores inventories, roles, collections, and vault keys, and connects to managed hosts.

Managed nodes

Linux or network targets execute modules remotely and do not need a persistent agent installed.

Inventory

Defines hosts, groups, connection variables, and metadata through static files or dynamic inventory plugins.

Modules and roles

Modules do the work while roles package repeatable defaults, tasks, handlers, templates, and vars.

Architecture and Components

Ansible separates intent from execution: inventories define where, playbooks define what, and modules or roles implement how that desired state is enforced.

  • Playbooks are composed of plays, tasks, handlers, variables, templates, and roles that converge systems into a known state.
  • Static inventory is simple for small estates, while dynamic inventory connects to cloud APIs, CMDB platforms, or virtualization layers.
  • Common modules include apt or yum for packages, copy and template for files, service for daemons, user for accounts, and docker_container for container workloads.
  • Jinja2 templating turns inventory variables into rendered configuration files, which makes host specific settings explicit and reviewable.
  • AWX or Tower adds RBAC, scheduling, credentials management, job templates, and a UI around the same Ansible content used from the CLI.

Key Concepts

Concept Purpose Operator note
Idempotency Running the same playbook repeatedly should leave systems in the same desired state. Prefer state driven modules over shell commands whenever possible.
Handlers Run only when notified by changed tasks and are ideal for restarts or reloads. Use them to avoid unnecessary service interruptions.
Vault Encrypts secrets such as passwords, tokens, and certificates in source control. Keep vault IDs and decryption keys outside the repository.
Dynamic inventory Builds host lists and variables from cloud or infrastructure APIs. Cache results when inventory resolution becomes slow.
Error handling Controls how failures are tolerated, rescued, or redefined. block, rescue, always, failed_when, and ignore_errors each fit different situations.

Playbook structure with handlers and roles

A clean playbook expresses desired state through tasks and delegates repeated logic into roles.

- name: Configure web tier
  hosts: web
  become: true
  roles:
    - common
    - nginx
  tasks:
    - name: Install packages
      apt:
        name: [nginx, curl]
        state: present
        update_cache: true
    - name: Render nginx config
      template:
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
      notify: restart nginx
  handlers:
    - name: restart nginx
      service:
        name: nginx
        state: restarted

Blocks, async execution, and tuning

Error handling and performance options are essential when many hosts or long running tasks are involved.

- name: Run risky change with rollback logic
  block:
    - name: Deploy package
      yum:
        name: app-suite
        state: latest
    - name: Run migration
      command: /usr/local/bin/migrate
      register: migration
      failed_when: migration.rc != 0
  rescue:
    - name: Restore previous package
      yum:
        name: app-suite-1.9.4
        state: present
  always:
    - name: Collect logs
      shell: journalctl -u app --since "10 minutes ago"
# ansible.cfg
[defaults]
forks = 25
pipelining = True
# async example
- name: Start a long running job
  shell: /usr/local/bin/reindex
  async: 1800
  poll: 15

Best Practices

  • Prefer roles and collections for shared automation so naming, defaults, handlers, and templates stay organized by domain.
  • Use host groups and variable precedence carefully; avoid duplicating the same variable in many places without a clear override strategy.
  • Choose modules before command or shell, because modules are usually idempotent, diff aware, and easier to lint or review.
  • Encrypt secrets with Ansible Vault and separate vault passwords from the repository through controller credentials or secure local storage.
  • Tune forks, SSH pipelining, fact gathering, and async execution for scale, and evaluate Mitogen only if your environment supports it safely.
  • Run playbooks in check mode when possible and use AWX or Tower for schedules, approvals, credentials, and audit history.

Troubleshooting

Symptom Likely cause Recommended action
Hosts unreachable SSH keys, sudo settings, hostnames, or Python availability on the remote system are incorrect. Use ansible all -m ping, verify ansible_user and privilege escalation, and bootstrap Python if the base image is minimal.
Tasks always report changed A shell or command task is not idempotent or the destination file differs every run. Replace shell with a stateful module, or add creates, removes, changed_when, or checksum aware templates.
Secret decryption failures The wrong vault ID or password source is being used for the encrypted files. Confirm vault IDs, review controller credential bindings, and test ansible-vault view on the target file.
Slow large inventory runs Fact gathering, serial package updates, or dynamic inventory lookups are taking too long. Disable unnecessary facts, increase forks, enable pipelining, cache inventory, and profile the slowest tasks.
